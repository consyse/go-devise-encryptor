# go-devise-encryptor

[![CI](https://github.com/consyse/go-devise-encryptor/actions/workflows/ci.yml/badge.svg)](https://github.com/consyse/go-devise-encryptor/actions/workflows/ci.yml)
[![Go Reference](https://pkg.go.dev/badge/github.com/consyse/go-devise-encryptor.svg)](https://pkg.go.dev/github.com/consyse/go-devise-encryptor)

A Devise encryptor written in Go. It lets a Go application read the
passwords in a Ruby on Rails database.

Ruby's bcrypt and Go's bcrypt both use the `2a` algorithm, so the hashes
are compatible.

The package is small and unaudited, but every release is tested against
hashes generated by Ruby's own `bcrypt` gem. Read the code, and check
that the behaviour below matches what your Rails app does.

# Installation

Go 1.24 or later.

    go get github.com/consyse/go-devise-encryptor

Import

    import "github.com/consyse/go-devise-encryptor"

The package name is `devisecrypto`.

# API

```go
// Devise 4.9 hashes at cost 12.
const DefaultStretches = 12

// bcrypt reads at most this many bytes of input.
const MaxPasswordBytes = 72

// Digest refuses any cost outside this range.
const MinStretches = 10
const MaxStretches = 31

// Returned by Digest for a cost outside that range (wrapped; check with errors.Is).
var ErrStretchesOutOfRange = fmt.Errorf(...)

// Returned by Digest and CompareErr when password or pepper contains a null byte.
var ErrNullByte = errors.New(...)

func Digest(password string, stretches int, pepper string) (string, error)
func Compare(password, pepper, hashedPassword string) bool
func CompareErr(password, pepper, hashedPassword string) (bool, error)
```

- `Digest` builds a Devise-compatible hash. `stretches` is the bcrypt
  cost, and must be between `MinStretches` and `MaxStretches`. Passwords
  or peppers containing null bytes return `ErrNullByte`.
- `Compare` reports whether the password matches the hash. It returns
  only true or false. Note the parameter order: `(password, pepper, hashedPassword)`,
  which differs from Go's `bcrypt.CompareHashAndPassword(hash, password)` and
  Devise's internal `Devise::Encryptor.compare(klass, hashed_password, password)`.
- `CompareErr` does the same work but also returns why it failed. A wrong
  password is `(false, nil)`. An unparseable hash or null-byte input is
  `(false, err)`. A blank hash (empty or whitespace) returns `(false, nil)`.
  Use it to tell a wrong password apart from a corrupt row in the database.

# Usage

If you don't have a pepper, pass the blank string `""`.

```go
package main

import (
	"fmt"

	"github.com/consyse/go-devise-encryptor"
)

func main() {
	password := "changeme"
	stretches := devisecrypto.DefaultStretches // 12
	pepper := "a really bad pepper"

	hashedPassword, err := devisecrypto.Digest(password, stretches, pepper)
	if err != nil {
		panic(err)
	}
	fmt.Println("hashedPassword: ", hashedPassword)

	// and to compare with a previously hashed password

	newPassword := "changeme"

	val := devisecrypto.Compare(newPassword, pepper, hashedPassword)

	if val {
		fmt.Println("Passwords are the same ")
	}
}
```

`DefaultStretches` is 12. That is the Devise 4.9 default, and also the
bcrypt gem's own `BCrypt::Engine::DEFAULT_COST`. Older Devise apps often
used 10. Use whatever value your Rails app has configured, or your hashes
will not match.

# The cost floor: we reject anything under 10

`Digest` returns `ErrStretchesOutOfRange` when `stretches` is below 10 or
above 31. It never adjusts the cost for you.

Because `Digest` wraps `ErrStretchesOutOfRange` with the received cost (using `%w`),
callers should test for it using `errors.Is(err, devisecrypto.ErrStretchesOutOfRange)`
rather than direct equality `==`.

That is a deliberate choice. It follows the same rule as the truncation
described below: copy Ruby where Ruby has a definite behaviour, refuse
where the two libraries would silently do different things.

Here they do different things. Below cost 4 neither one tells you:

| `stretches` | Go's bcrypt | Ruby's bcrypt |
| --- | --- | --- |
| 0 and below | silently uses 10 | raises `InvalidCost` |
| 1 to 3 | silently uses 10 | silently clamps to 4 |
| 4 to 31 | uses it | uses it |
| 32 and above | raises | raises |

So there is no bad cost that both sides handle the same way. A silent
change of work factor is worse than an error, because you only find out
years later, when the hashes are already in the database.

The floor is 10 rather than bcrypt's own minimum of 4 because 10 is the
weakest cost a real Devise app would use. Anything lower is a
misconfiguration, not a choice.

**`Compare` is not affected.** It never looks at `stretches`. bcrypt
stores the cost inside the hash string, so `Compare` still verifies a
cost-4 hash that an old Rails app wrote. Only new hashes are held to the
floor. The test suite proves this: the Ruby fixtures are generated at
cost 4 on purpose.

# The 72-byte limit: we truncate on purpose

bcrypt only reads the first 72 bytes of its input. Devise appends the
pepper to the password before hashing, so a short password plus a long
pepper can cross that line.

**This library truncates password + pepper at 72 bytes. It does not
return an error.**

That is a deliberate choice, not an oversight:

- Ruby's bcrypt silently truncates at 72 bytes and produces a hash.
- Go's `golang.org/x/crypto/bcrypt` refuses instead, and returns
  `ErrPasswordTooLong`.
- A hash already stored by Rails was built from those truncated bytes.
  If we returned an error, we would reject credentials that the Rails
  app accepts today.
- Agreeing with a live Devise database is the entire purpose of this
  package. So we follow Ruby, not Go.
- The bytes past 72 add no security anyway, because bcrypt never reads
  them.

If you want to reject long passwords, check the length yourself before
you call `Digest`. `MaxPasswordBytes` is exported for that.

# Whitespace peppers
 
Devise checks the pepper with `pepper.present?`. A pepper of `"   "` is
blank to Ruby, so Devise hashes the password on its own.

This package does the same. A whitespace-only pepper is treated as no
pepper at all.

# Null bytes: we reject them

Ruby's `bcrypt` gem refuses any secret with a null byte (`\0` / `0x00`),
raising `ArgumentError: string contains null byte`. Go's bcrypt silently
processes them.

Allowing a null byte in Go would write hashes into the database that Rails
crashes on when the user tries to authenticate. So `Digest` and
`CompareErr` return `ErrNullByte` instead.

# Blank hashes: matching Devise

Devise guards against unconfigured passwords with
`return false if hashed_password.blank?`. In Rails, `.blank?` matches
empty strings (`""`) as well as whitespace-only strings (`"   "`).

`Compare` and `CompareErr` treat any blank hash as a non-match
(`false, nil`), not as an unparseable hash error.

# Timing attacks and user enumeration

Like Devise, `Compare` and `CompareErr` return immediately (`false, nil`) when
`hashedPassword` is blank, avoiding an unnecessary bcrypt computation.

However, because computing bcrypt takes noticeable time (~100ms or more depending on stretches),
returning immediately for missing accounts or blank hashes allows timing-based account
enumeration. Callers requiring protection against user enumeration should perform a dummy
bcrypt comparison against a placeholder hash when an account does not exist.

# Running the tests

    go test ./...

Some tests compare Go against hashes that Ruby generated. Those need
Ruby and the `bcrypt` gem:

    gem install bcrypt

To regenerate the stored fixtures:

    ruby script/generate_fixtures.rb

That writes `testdata/devise_hashes.json`.

If Ruby is not installed, the cross-language tests skip. The rest of the
suite still runs, so `go test ./...` passes on a machine without Ruby.
